## How structure grows

Source: <https://diataxis.fr/how-to-use-diataxis/>.

diataxis.fr describes documentation as well-formed organic growth: healthy structure develops from within, like an organism built up one cell at a time, not imposed from above. Following the workflow, you improve pieces; at some point those changes appear to demand that material move under a certain heading, and that is how the top-level structure forms. Diátaxis changes the structure "from the inside".

For proposals, this means a move under a new heading is justified by content that already exists and already reads in that mode: three how-to guides buried in a "Usage" page can become a "How-to guides" section. A heading for content that does not exist yet is never justified.

Section names need not be the mode names. diataxis.fr suggests *Discussion*, *Background*, *Conceptual guides* or *Topics* for explanation ([explanation](https://diataxis.fr/explanation/)). Keep a name the project already uses if it fits the content.

## Landing pages

Source: the "complex hierarchies" page, removed from diataxis.fr in 2026-08 (see `sources.md`), last published text at <https://github.com/evildmp/diataxis-documentation-framework/blob/0c9022ecbd82f8cd42069886faae40cd91eb8995/complex-hierarchies.rst>.

That page gave this guidance for contents and landing pages:

- A landing page should read like an overview: introduce what is below it, with headings and short introductions, not just list links. It stressed writing for a human reader, not filling in a scheme.
- Lists longer than about seven items are hard to read unless they have a mechanical order (alphabetical, numerical). Break longer ones into groups, if needed with another layer of hierarchy.
- If applying Diátaxis leads to a format that seems uncomfortable or ugly, apply it differently: the reader's experience is what matters.

Since the page is no longer on the live site, say so when you rely on it.

## Several audiences, platforms or products

Source: as for landing pages.

When the four modes meet another axis (users, developers and contributors; or one product on several platforms), the removed page said Diátaxis is not four boxes that documentation must be placed in. The structure may put audiences first and modes inside each, or modes first and audiences inside, or mix the two, as long as the modes are not muddled within any part. Start from how the product looks to each audience: if users on two platforms do quite different things, document what each of them sees. Documentation can be as complex as it needs to be, provided it stays logical and navigable.

## Finding the navigation in a docs tool

This section is this skill's own, not from diataxis.fr. Read the project's configuration before proposing a move, because in some tools the folder layout *is* the navigation, and a file move silently changes what readers see. If a tool is not listed, or the project's version behaves differently, read the tool's documentation for the installed version.

| Tool | Where the navigation lives |
| --- | --- |
| MkDocs | `nav` in `mkdocs.yml`. Without it, navigation is generated from the files in `docs_dir`. |
| Zensical | `nav` under `[project]` in `zensical.toml`, or `nav` in a `mkdocs.yml` it reads instead. Without it, navigation is generated from the files. |
| Sphinx | `toctree` directives in the source files, starting from the root document (usually `index.rst` or `index.md`). |
| Docusaurus | `sidebars.js` or `sidebars.ts`. An `autogenerated` sidebar follows the folder tree, with `_category_.json` or `_category_.yml` files and `sidebar_position` front matter setting labels and order. |

Make the nav change in the same proposal as the content change that needs it, and never restructure the nav ahead of content.

## Moving a published page

Also this skill's own. A move breaks bookmarks, search results and links from elsewhere. In the same proposal:

- update every internal link to the page (search the docs for its old path and title)
- propose a redirect if the project already has a redirect mechanism, such as the `mkdocs-redirects` plugin, Zensical's redirects, `sphinx-reredirects`, or `@docusaurus/plugin-client-redirects`
- if it has none, say so and let the user decide whether to add one; adding a dependency is their call
